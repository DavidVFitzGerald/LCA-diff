Here is a description of how certain parts of the app should work:
- The user can compare the unit processes of different databases for which they have a license for. They can select any number of unit processes from any number of databases in order to compare them.
- Since the app must be able to handle different databases, one common nomenclature should be used for all databases. This means there should be a translation from the nomenclature of the raw data to the common nomenclature happening at some when the data is loaded.
- For the MVP, the loading of the databases should not be done by users, it should be done during the development and maintenance of the app. Users should not need to host the data on their machines. For a future version, users should be able to upload their database files.
- For the MVP version of the app, only one database should be included, BAFU:2026, but the translation to a common nomenclature should be implemented already.
- To help design the pipeline for loading the BAFU:2026 database, I have attached a sample of 5 xml files (out of 11947) that contain the data for unit processes (one file per unit process), 3 files that describe the xml schema (ecoSpold) which might not necessarily be followed exactly by the unit process files, and one Excel file that contains the Life Cycle Impact Assessment (LCIA) scores of all unit processes for many different impact methods (one column per impact assessment method/impact category).
- The interface should have a main pane in the central area of the window where the unit processes selected by the user are shown side-by-side. The selection of unit processes should happen on the left side of the window. The databases and corresponding tree-like list of unit processes should be shown by default, with the option of collapsing it to make more space for the comparison pane. Similarly, when comparing impact scores, the list of methods and indicators should be shown on the right side of the window and be collapsible. Tabs at the top of the comparison pane should allow to switch between aspects that are being compared, for the MVP that would be just "Flows" and "Scores”. At the top of the window there should be a header section spanning the entire width of the window, with the app name (“LCA diff”) on the left, and login button and settings on the right.
- When a user goes to the webpage of the app, the landing page should be a login page, with the app name shown in large font in the central area, with login fields (username and password) below). Once a user logs in, they should see the interface as described above.
- On the left side of the web interface, the user should be able to expand the databases in a tree-like way, in order to view the list of unit processes. If the unit processes have labels (such as category) that groups them, that’s what should be shown as first level when the user clicks on a database to expand it.
- The user should be able to tick the unit processes they want to compare. There must also be a search window just above the list which allows users to filter for unit process name, geography, category, subcategory, or name of the reference flow. The search window should by default be for searching by unit process name, but a more detailed search window should be possible to toggle to enable search for the other fields mentioned. More fields than those mentioned here could be added to the search functionality in the future.
- When filtering based on search terms, only the unit processes that match the search criteria should be shown. The search should be reactive, meaning the list automatically updates as the user types characters in the search window.
- The search window should have a button that allows to clear the search window with one click.
- Any unit processes that is ticked (for selection for comparison) should be directly shown in the central area of the window.
- The default outcome of ticking a unit process is that the inputs and outputs of each unit process are listed in the central area of the window, with the flow names on the left side, and the unit process names at the top. By unit process names, I mean the "Process Name", "Location" (in the case of BAFU:2026, this is the "location" attribute of the "geography" tag in the unit process files).
- If one or more unit processes contain the same input or output, those should be represented on the same row. The databases usually have a unique identifier for flows. In the case of BAFU:2026, it is the attribute called “number” in the “exchange” element. The unique identifier should be in the database table that is serving the data to the web interface. This identifier along with the “Type” (inputGroup or outputGroup in BAFU:2026) is what should be used to align the flows in the comparison pane.
- Each row should have a vertical bar chart, where a bar should be present in the column of every unit process that contains the flow corresponding to that row. If the amounts of all flows are positive or 0/absent, then the base of the bar chart should be placed close to the bottom border of the row. If there is one or more unit process in which the flow has a negative amount, then the base of the bar chart should be shifted higher, and the negative values should be shown with bars that go below the horizontal axis. If the flow amount is negative or 0/absent for all unit processes, the base of the chart should be placed close to the top border of the row.
- Each row should not be delimited by borders, but rather a different shade of background colour.
- The vertical bars representing the flow amounts should be filled green for the maximum value, and lighter as the values are closer to 0. Same for negative values but with the colour red.
- The total height of each row should be normalized based on the maximum of absolute values of all flows for the given flow. So if for example for one flow (row), the values range from 0 to 12 between all unit processes compared, the vertical bar for the value 12 should take the full height of the row (minus padding). If the values are negative, for example -0.2 to -0.5, the vertical bar of the value -0.5 should correspond to a height of 1. If the values range from -32 to +61 (mix of positive and negative flow amounts), then the total row height should be (61+32)/61 = 1.5246. This means that rows that contain both positive and negative values will take up more vertical space than the rows that don't.
- The base of the chart should always be placed at y=0.
- The label that shows the flow amount should contain just the value, no unit, and should always be placed just above the horizontal axis, except when all values are 0/absent or negative, then the labels should be shown below the horizontal axis.
- A label with the flow amount should be shown for all unit processes that have that flow in their list of flows, also if the flow amount is 0. If the unit process does not contain that flow, there should be no label (a flow with amount 0 is not the same as no flow at all).
- The rows should be updated whenever the user selects (ticks) or deselects (unticks) a unit process from the list of unit processes.
- If a flow is only present in one of the currently selected unit processes, the row corresponding to that flow should be removed as soon as the unit process that contains that flow is unticked.
- The rows should be ordered vertically by "Type", which corresponds to the "inputGroup" and "outputGroup" fields in the BAFU:2026 database. For the common nomenclature, the inputGroup and outputGroup should be translated to the following terms:
    - inputGroup = 0: "Reference Flow"
    - inputGroup = 5 and flow amount ("meanValue" in BAFU:2026) is positive: "Technosphere Input"
    - inputGroup = 5 and flow amount ("meanValue" in BAFU:2026) is negative: "Technosphere Output"
    - inputGroup = 4: "Ecosphere Input"
    - outputGroup = 4: "Ecosphere Output"
- The “Type” should be the first column identifying flows (meaning it should be shown as first field on the left side). Each row should be further identified by the following fields: "Flow Name", "Location", "Process Name", "Category", "Subcategory", "Unit"
- The Process Name is only relevant for the reference flow and technosphere flows. For BAFU:2026, it is not indicated as string in the "exchange" element in the unit process xml files. Instead, there is a "number" attribute that refers to the number of the unit process, which is the "number" attribute of the "dataset" element/tag. This number should be used to retrieve the Process Name for technosphere flows. It should also be used to retrieve the Location of technosphere flows (but not ecosphere) even though the location might be indicated in the flow/exchange element.
- The Location might never be indicated for ecosphere flows in BAFU:2026, but it might be indicated in other databases. The Category and Subcategory should normally be indicated for all types of flows in BAFU:2026, but it might be empty for flows in other databases.
- For the default grouping/ordering of flows, the type should be used first, followed by the category, subcategory, and flow name. Alphabetical order for these last three fields. For the type, the following order should be used: Reference Flow, Technosphere Input, Technosphere Output, Ecosphere Input, Ecosphere Output.
- In a future version, users should be able to easily change the order of the rows/flows directly in the main window.
- The user should be able to drag the columns that represent unit processes to change their order. When hovering the mouse on one column/unit process, a small x should appear in the top left corner of that column, above the name of the unit process, that allows the user to remove the unit process from the comparison view (main window). This is equivalent to deselecting/unticking the unit process from the list of unit processes on the left side of the interface.
- For the MVP, in addition to comparing the flows of unit processes, the user should be able to compare impact scores. Switching to the comparison of impact scores should be done via tabs mentioned earlier, which should be shown in the top-left corner of the comparison window. By default, the first tab should be the one for Flows. The second tab should be named "Scores". For future versions, after the MVP, additional tabs should be made available, primarily, a tab that shows metadata fields (mainly text fields that describe the unit processes) side by side. But for the MVP we want just the Flows and Scores.
- When selecting the Scores tab, the selected unit processes should be shown as on the Flows tab, but instead of rows showing the flows, the rows should show the scores of the different impact assessment methods/categories/indicators.
- By default, there should be just the IPCC 2021 GWP 100 indicator shown. The list of impact assessment methods should be shown on the right side of the comparison window. The impact assessment method indicator names are generally composed of two or three parts: the method name (always available), followed by the category name (optional), then the indicator name (always). In  BAFU:2026, the scores are provided in the Excel file attached, in the sheet “BAFU_2026 v1”. There is no category name. The method name is indicated in the first row, while the second row contains the indicator name. The scores are contained in columns E to AY.
- When loading the raw data of the BAFU database, the list of unit processes shown in the Excel file should be validated against the unit processes contained in the xml files. A database table should be created where each row contains the identifier (“number” attribute) of the unit process, along with the scores contained in the Excel sheet. In the case of the BAFU database, the xml files are considered to be the correct source of truth. In case of mismatch, an additional mapping might have to be provided. How this mapping is provided should be managed according to best practices when it comes to handling databases such as these.
- For the list of indicators shown on the right side of the user interface, the default view should only show method names. The user should be able to expand a method to see the full list of indicators. If the method provides category names, these should be shown as a sublevel in the list, but expanding the method should automatically show all indicators, with a kind of tree structure to make it clear to which method (and optionally category) they belong to.
- The comparison should compare the impact scores the same way as for flow amounts (vertical bar graphs, which handle both positive and negative values).
- Each row should be identified with the following fields: "Method", "Category" (empty if no category is provided in the source data), "Indicator", "Unit".
- Each column header should be the same as for the Flows tab, showing the Process Name and Location of the unit process. However, the reference flow needs to be shown in the header as well, along with the unit and amount.
- When the user selects more indicators in the list, a row should be added for each indicator selected. For the MVP, the order of the rows should be the same as the list, which should be the same as the order in the raw data of the given database (in this case BAFU:2026 for the MVP).
- If the user unticks/deselects an indicator in the list, the corresponding row should be removed.
- Contrary to flows, for the scores provided with a given database, the unit processes of that database will have a score defined for all indicators. This means there should always be a label. Although it may often be just a value of 0.
- The user should be able to view 1 up to hundreds of unit processes side-by-side (e.g. if they want to compare all unit processes that produce electricity, that might involve a lot of unit processes). What might be necessary to change when many datasets are shown is how the text of the unit process headers are presented. It might make sense to make the columns thinner than when having selected just 1-5 unit processes. In a post-MVP version, it should be possible to zoom in and out. But for the MVP, and in any case the default view, the columns should have a certain max width which is maintained up until a certain number of unit processes are selected. Beyond that number, the width should dynamically be made smaller as the user selects more unit processes to compare, but only down to a minimum limit. Once that limit is reached, the user should instead have to scroll to the right to see the additional processes they added. In a post-MVP version, the user should be able to zoom out (regardless of how many unit processes are selected). The way the width of the columns is modified based on the number of unit processes and the size of the browser window should be the same regardless of which tab is selected (Flows, Scores, or others in the future). However, the min and max width settings might need to be different per tab. The values for Flows and Scores can be set the same (but stored separately already for the MVP).
- For how the data of the databases is loaded and stored, we are considering the following:
- We want to stored the raw data as is, along with metadata such as date published (to be provided by the admin/whoever is uploading the database to the app), upload date, tag to identify all files that are part of a certain database and version.
- The raw data should then be extracted into another form, which most likely makes sense to put in a database, keeping all field names and content as provided in the raw data. For the MVP, only the data that is needed for the MVP should be extracted from the raw data into the database tables (or other suitable intermediate storage).
- The extracted data should then be transferred to a final database which uses the harmonized nomenclature. That means that this “final” database would contain data from multiple databases as well multiple versions of a given database (e.g. BAFU:2026 and BAFU:2027). The way that the data is stored in this “harmonized” database (or whatever storage is best) should be such that showing data into the web interface should be very fast, regardless of how many different databases the user selects unit processes from, and also regardless of whether the user is just selecting 5 datasets or 100.
- For the MVP, there are no calculations happening at any point in the pipeline. However, for post-MVP, some calculations may be performed, for example, calculating scores for multiple databases using a common set of methods. Such calculations should happen when the app is updated, not as result of the user selecting unit processes and indicators in the user interface. Basically, what the normal user sees should always have been pre-calculated and stored somewhere in the backend of the app.
- Future considerations:
    - The different databases might have their impact scores recalculated with a common set of impact assessment methods. The recalculated scores would be the ones compared. For the MVP, the scores provided by the database providers are used, meaning that they should not be stored in a common table with the scores of unit processes of other databases.
    - Users should be able to save comparisons that they make so that they can reopen them the next time they log in.
